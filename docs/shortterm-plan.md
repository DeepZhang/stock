# 短线选股系统开发任务书（给 Codex）

> 目标：给 stock 网站加一个“比较强大”的短线选股功能：选出靠谱、适合短线、胜率高的票。
> 工作地点：InstaBox 盒子（开发工作台）。代码仓库：https://github.com/DeepZhang/stock.git（私有库）。
> 部署目标：scnet 容器里的 live 站（Flask + RAKsmart 隧道，http://198.200.58.179:5000）——盒子只负责开发，部署由 Muse 另行操作，Codex 不要碰线上。

## 0. 背景数字（回测结论，v1.1，训练期 2015–2023，检验期 2024–2026）

- A 股以均值回归为主，动量/放量追涨无效。
- 涨停次日：次日 +2.04%，胜率 57–58%，最稳的短线信号，持有 1 天。这是主策略。
- 超跌反弹：5 日跌超 8% 后 20 日 +3.70%（检验期）；RSI≤20 后 20 日 +15.10%（检验期含 2024-09 大反弹，偏高；训练期仅 +2.26%，regime 依赖强）。适合 3–5 日持有，副策略。
- 放量突破：两段都跑输全市场均值，胜率仅 44–46%，已降级，不要做主策略。
- 量比最高组与 RSI 最高组 20 日收益最差——追高是反向指标，禁止追高。
- 现有代码：`modules/stock_screener.py` 已有三策略（oversold / limit_up / breakout），`run_screen()` 输出分桶；`stock-analysis/` 有回测脚本与 `pattern_results.json`；`app.py` 有 `/api/screen`（返回扁平 list 并写 `data/stock_picks.json`）与 `/api/prediction`。

## 1. 红线（违反即返工）

1. 只选股，不交易：不下单、不接交易接口、不碰任何资金操作。
2. 每个信号/过滤器必须有回测数字（胜率、平均收益、样本数 n、检验期），没测过的数字不准写进页面和报告。
3. 不破坏现有契约：`/api/screen` 仍返回扁平 list 并写 `data/stock_picks.json`；`/api/prediction` 仍读 `stock/data/prediction.json`。
4. 密钥绝不进仓库：`config.json`、`*_auth.json`、`.env`、历史 parquet、日志一律不提交。先跑 `git ls-files | grep -E 'config\.json|_auth\.json|\.env'` 检查——如果 `config.json` 已在仓库里，立即 `git rm --cached` 移除追踪并报告（轮换密钥由用户处理）。
5. 自测通过才能提交（见第 5 节）；每次提交一个逻辑改动，提交信息写清楚（见第 6 节）。

## 2. Phase 1：短线选股引擎 v1（先做这个，跑通再谈 Phase 2）

### 2.1 主策略：涨停次日（持有 1 天）

在现有 `strat_limit_up` 基础上加过滤与评分，不要只返回“今日涨停”：

- 硬过滤（缺一不可）：
  - 非 ST、非退市整理、非停牌，当日可交易。
  - 排除一字涨停（开盘即封死、全天未打开，买不进）。
  - 日成交额 ≥ 1 亿元（流动性门槛，数值要回测确认，不可拍脑袋）。
  - 当日换手率在合理区间（过低买不进、过高接盘风险大；区间由回测定）。
- 位置过滤（回测决定取舍）：
  - 首板 vs 连板（2 板及以上）分开统计胜率；高位连续涨停后（例如 3 板以上且累计涨幅过大）剔除或降权。
  - 封单强度：封单金额 / 成交额，封单越强越好（阈值回测定）。
  - 量比适中：量比过高（爆量）要扣分，禁止无脑追爆量板。
- 输出每只候选：代码、名称、信号类型、涨停板数（首板/连板）、当日涨幅、换手、量比、封单强度、成交额、预期胜率（同类历史胜率）、买入参考价（次日开盘/集合竞价参考）、止损位（买入价 -3%）、止盈规则（次日冲高了结为主，见 2.3）。
- 排序：按预期胜率降序，取 Top 10；同胜率按成交额降序。

### 2.2 副策略：超跌反弹（持有 3–5 天）

- 沿用现有 `strat_oversold`（5 日跌超 8% 或 RSI14 ≤ 20），加过滤：
  - 剔除基本面暴雷（近期大幅下修业绩、立案调查等公开利空——先做关键词规则版，后续再接公告源）。
  - 要求 RSI 超卖与 5 日跌幅双条件叠加的优先（双信号比单信号胜率高，回测验证）。
  - 止损：买入后跌破近期低点或 -5% 止损。
- 与主策略分开展示，不要混排（持有期不同）。

### 2.3 卖出纪律（写进每只票的计划里）

- 涨停次日：次日开盘冲高（例如 +3% 以上）分批了结；开盘低开且跌破 -3% 止损；尾盘仍未冲高则收盘前了结，不隔夜。
- 超跌反弹：持有 3–5 天，到期按规则了结；期间跌破止损位立即出。
- 所有规则都要有回测依据；回测没覆盖的写法不准编数字。

### 2.4 回测验证（Phase 1 的核心交付物，不可跳过）

- 回测脚本放在 `stock-analysis/`（复用 `analyze_patterns.py` 的口径：RSI 用 Wilder ewm alpha=1/14；涨停 9.5% 阈值；收益用前复权收盘价）。
- 数据：用 `pull_history.py` 从东财拉历史（盒子里可直连东财），缓存到 `data/history/`（gitignore，不提交）。全量拉取太慢时先拉 2024–2026 检验期 + 流动性前 1500 只，样本量写进报告。
- 每个过滤器单独出报告：加过滤前 vs 加过滤后（胜率、平均收益、样本数 n），胜率没提升或样本数过小（n < 50）的过滤器砍掉。
- 输出 `stock-analysis/shortterm_backtest.md`：主策略与副策略的胜率/盈亏比/样本数、每个过滤器的提升表、结论（哪些过滤保留、哪些砍掉）。

## 3. Phase 2：评分模型（Phase 1 跑通并验收后再做）

- 目标：给候选票打分排序，不是替代规则。规则先筛，模型再排。
- 样本：历史数据生成带标签样本——特征（涨跌幅、RSI、量比、换手、均线位置、涨停板数、封单强度、成交额、市值）→ 标签（未来 1/3/5 日涨跌，涨为正样本）。
- 训练集 2015–2023，验证集 2024–2026；先上 XGBoost/LightGBM（快、可解释）；Qwen LoRA 也可以，但要先证明比规则排序强，否则不用。
- 验收：模型排序的 Top 10 胜率必须高于规则排序的 Top 10，否则砍掉模型、只用规则。
- 注意：昨天练的两个 LoRA（0.5B/1.5B）是客服问答模型，与交易无关，禁止复用。

## 4. Phase 3：网站与每日任务（Phase 1 验收后做）

- 新页面 `static/shortterm.html` + 路由 `/api/shortterm`：展示当日候选（主策略 Top 10、副策略 Top 10），每只含信号类型、预期胜率、买入参考、止损位、止盈规则；再加历史回测页（各信号的历史胜率/盈亏比/样本数）。
- 每日任务脚本 `scripts/run_shortterm.py`：收盘后跑增量数据 → 信号扫描 → 过滤评分 → 写结果 JSON → 供页面读取。复用现有 `push_summary.py` 的推送口径，出一条当日候选摘要（飞书/微信复用现有通道）。
- 样式与现有页面保持一致，不要引入新重型前端依赖。

## 5. 自测要求（每次提交前必须跑）

1. 单元自测：每个新函数配一段可运行的自测（`python -m pytest` 或脚本内 `if __name__ == "__main__"` 自测块），覆盖边界（ST、停牌、一字板、数据缺失）。
2. 回归自测：固定日期（2026-11-06）跑全量筛选，与已知值对照（超跌 33、涨停 14、突破 30 为 v2 基线数量级，数量对不上要查原因，不要改数字凑数）。
3. 回测自测：回测脚本跑通且输出报告文件，数字自洽（胜率 = 胜场 / 样本数）。
4. 网站自测：Flask 起服务，`/api/shortterm` 返回 200 且字段齐全，页面能打开。
5. 全部自测通过才能 `git commit`；自测失败的提交一律不推。

## 6. 提交规范（每次提交都要遵守）

- 一个提交只做一个逻辑改动；先在分支 `feature/shortterm-picks` 上开发，跑通后再合到主分支。
- 提交信息格式：`<范围>: <做了什么>（<依据/回测结果>）`，例如：
  - `screener: 涨停次日加换手过滤（检验期胜率 58%→61%，n=312）`
  - `screener: 剔除一字涨停（买不进，n=47）`
  - `web: 新增短线选股页 /api/shortterm`
- 禁止写 `update`、`fix`、`优化` 这种没信息的提交信息；禁止把自测失败的代码推上去。
- 每个 Phase 完成时写一段中文总结（改了什么、回测结果、自测结果）交给 Muse 验收。

## 7. 环境与注意事项

- 盒子是 Ubuntu 桌面，4 核 8G，闲置会休眠——开发时保持使用，跑长回测前确认盒子处于唤醒状态；回测分段跑，断点续跑，不要一次跑全量 5563 只×10 年还不设检查点。
- Python 依赖：复用现有 `requirements`（pandas、flask 等）；Phase 2 要装 xgboost/lightgbm 时先确认能装上（有 wheel 优先），装不上就停下报告，不要硬编。
- 东财数据源在盒子里可直连；拿不到数据时先报问题，不要编造行情。
- 有任何拿不准的（数据口径、回测方法、部署细节）先停下问 Muse，不要猜。
